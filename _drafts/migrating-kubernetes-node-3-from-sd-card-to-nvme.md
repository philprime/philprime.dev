# Working notes, not a publishable article

Goal: migrate `kubernetes-node-3` from booting Raspberry Pi OS on an SD card with NVMe-backed data to booting fully from NVMe, then repeat for node 1. Preserve existing cluster and storage data. Node 2 already boots from NVMe, while nodes 1 and 3 initially boot from SD cards. The operator has physical access if needed. These are chronological field observations, not a polished migration procedure or proof of availability under failure.

## Access and context

- Direct SSH to node 3: `ssh -i ~/.ssh/k8s_cluster_id_ed25519 pi@10.1.1.3`. Nodes 1 and 2 use the corresponding `.1` and `.2` addresses. There is also an externally reachable SSH entry point provided by the operator, but direct access worked.
- Local `kubectl` defaults to a _different_ production cluster. Always use `kubectl --context admin@k8s-pi-cluster-tailscale ...` for this Raspberry Pi cluster. An initial read-only `kubectl get` without `--context` queried the other cluster. No changes were made there.
- SSH as `pi` did not have working default `kubectl` credentials (`the server has asked for the client to provide credentials`). `sudo -n kubectl --kubeconfig=/etc/kubernetes/admin.conf get nodes -o wide` on node 3 worked, but local `kubectl` with the explicit Pi context is preferred.
- Reference: the existing guide at `guides/building-a-production-ready-kubernetes-cluster-from-scratch/` and the companion NVMe rebuild article `_posts/2026-06-05-setup-raspberry-pi-kubernetes-node-with-nvme.md`. That article describes rebuilding a _failed_ node 2 directly onto NVMe and rejoining the cluster. Node 3 is different: its NVMe already contains live data, so copying or flashing an OS onto the whole device would destroy it.

## Read-only node 3 inspection

- OS: Debian 12 Bookworm. Kubernetes node reports `v1.31.7`; node 2 is Debian 13 Trixie on `v1.32.13`, and node 1 is Bookworm on `v1.31.7`. All three reported `Ready`.
- `lsblk` showed the 59.5 GiB SD card at `mmcblk0` with a 512 MiB FAT partition mounted at `/boot/firmware` and a ~59 GiB ext4 root partition mounted at `/`. The NVMe device is `nvme0n1`, 465.8 GiB, with one ext4 partition `nvme0n1p1` mounted at `/mnt/nvme`. Additional `/dev/sd*` devices are Longhorn volumes, **not** install targets.
- `df -hT` showed `/` (SD card) at 8.7 GiB used, `/boot/firmware` at 68 MiB used, and `/mnt/nvme` at 46 GiB used with ~389 GiB available. This is not empty storage.
- NVMe filesystem root contains `containerd/`, `kubelet/`, `storage-1/`, and `lost+found/`. Container runtime, kubelet state, and distributed storage may be actively using these directories. Do not overwrite, repartition, or relocate them without a deliberate migration and backup strategy.
- `/etc/fstab` mounts the SD partitions using `PARTUUID=8a438930-01` at `/boot/firmware` and `PARTUUID=8a438930-02` at `/`; NVMe uses `/dev/nvme0n1p1 /mnt/nvme ext4 defaults 0 0`.
- `/boot/firmware/cmdline.txt` points at `root=PARTUUID=8a438930-02` and includes `cgroup_memory=1 cgroup_enable=memory`.
- `rpi-eeprom-config` returned `BOOT_ORDER=0xf461`. Exact boot-order implications and any required firmware changes have not yet been validated against the current hardware and OS. No boot changes made.

Controller-manager and scheduler similarly run on all three nodes. Losing node 3 would leave two of three etcd members, the minimum quorum, provided both remaining members and their network remain healthy.

- `cert-manager`, `cert-manager-cainjector`, and `cert-manager-webhook` each have **one** running replica, all on node 3. The cert-manager PDB has `ALLOWED DISRUPTIONS=0`. A straightforward eviction/drain may be blocked, and loss of node 3 interrupts these services until rescheduled. This needs deliberate mitigation and verification before downtime.
- `dns-system/etcd-dns` has three running pods across all three nodes; its PDB currently allows one disruption. Confirm quorum and volume health before removing node 3.
- `postgresql` is a healthy three-instance CloudNativePG cluster across nodes 1, 2, and 3. The current primary is `postgresql-4` on **node 3**. The primary PDB allows zero disruptions. Plan and verify a safe switchover/failover before draining or powering off node 3. Do not assume a healthy cluster means zero client interruption.
- Longhorn has a manager, CSI plugin, engine-image pod, and instance-manager on each node. Longhorn reports attached, healthy volumes for the node 3 `etcd-dns-2` and `postgresql-4` pods. Other volumes are attached to nodes 1 and 2; two detached Renovate volumes show `unknown` robustness and need interpretation before any blanket assertion that storage is fully healthy. The NVMe-backed `storage-1/` directory is likely important to Longhorn and requires inspection. Confirm replica placement and rebuild/scheduling health before taking node 3 offline.
- Two active GitHub Actions runner pods are on node 3, each with a bound `local-path` PVC. These are node-local and may interrupt ongoing CI work; identify retention and scheduling requirements before maintenance. Several GitHub ARC listener pods also run there.
- Some other single-replica services run on nodes 1 or 2, but are not themselves made highly available by the three-node control plane. High availability of the cluster control plane is not the same as high availability of every workload.
- These checks are a snapshot only. No node has been cordoned, drained, powered off, or modified so far.

## First maintenance changes: prevent new scheduling

The operator agreed to cordon node 3 and stop Longhorn scheduling new replicas there. Performed with the explicit Pi cluster context:

```bash
kubectl --context admin@k8s-pi-cluster-tailscale cordon kubernetes-node-3
kubectl --context admin@k8s-pi-cluster-tailscale patch nodes.longhorn.io kubernetes-node-3 -n longhorn-system --type merge -p '{"spec":{"allowScheduling":false}}'
```

Before the change, Kubernetes `spec.unschedulable` was unset, Longhorn node `spec.allowScheduling` was `true`, and its `storage-1` disk had `allowScheduling: true`. Both commands succeeded. A subsequent `kubectl get nodes` showed `kubernetes-node-3 Ready,SchedulingDisabled`; the Longhorn node has `spec.allowScheduling: false`. The per-disk setting remains `true`, but the node-level scheduling setting is off. Its Longhorn `Schedulable` status also reads `False` with message `Node kubernetes-node-3 is cordoned`. No drain or eviction was attempted.

**Important distinction:** cordoning prevents new ordinary pods, and disabling Longhorn scheduling prevents new Longhorn replica placement. Neither moves existing workloads or Longhorn replica files off the NVMe. Read-only inspection after these changes showed eight Longhorn volumes configured for three replicas each, with one active replica on **each** of nodes 1, 2, and 3 for every volume. Six attached volumes reported `healthy`; the two detached Renovate volumes reported `unknown`. Node 3 therefore still holds an active replica of all eight volumes, including PVCs whose workloads are currently attached elsewhere. Removing node 3 leaves only two distinct storage nodes, so there is no third distinct host for three-way replication during the maintenance window. Do not confuse `allowScheduling: false` with completed replica evacuation. Confirm the intended degraded-redundancy tolerance and backup/recovery position before shutdown, disk changes, or replica eviction.

## PostgreSQL switchover and node drain

Operator requested a primary switch off node 3, then a drain. Before issuing any switchover command, inspection showed CloudNativePG had **already switched automatically** from `postgresql-4` on node 3 to `postgresql-5` on node 1 as a consequence of cordoning node 3. A PostgreSQL namespace event said: `Current primary is running on unschedulable node kubernetes-node-3, switching over from postgresql-4 to postgresql-5`. The old primary's container restarted cleanly and became a replica. At this point CloudNativePG reported `Cluster in healthy state`, three ready instances, and continuous archiving working. We did not trigger a second or manual failover.

The first `kubectl drain kubernetes-node-3 --ignore-daemonsets --timeout=90s` refused to proceed because several pods use `emptyDir`; this attempt did not evict pods. Cert-manager's sole controller replica on node 3 also had a PDB with zero allowed disruptions. We temporarily scaled its controller Deployment from one replica to two:

```bash
kubectl --context admin@k8s-pi-cluster-tailscale scale deployment cert-manager -n cert-manager --replicas=2
kubectl --context admin@k8s-pi-cluster-tailscale rollout status deployment cert-manager -n cert-manager --timeout=120s
```

A new ready controller landed on node 2 and the PDB allowed one disruption. Cainjector and webhook each remained single-replica, but had no corresponding PDB and could reschedule. The cluster's Longhorn `node-drain-policy` was `block-if-contains-last-replica`. A second drain used standard eviction, honored PDBs, and explicitly allowed disposal of pod-local `emptyDir` data:

```bash
kubectl --context admin@k8s-pi-cluster-tailscale drain kubernetes-node-3 --ignore-daemonsets --delete-emptydir-data --timeout=120s
```

The Longhorn instance-manager PDB initially denied eviction while other pods/volumes were attached; after they moved the eviction succeeded, and `kubectl` reported `node/kubernetes-node-3 drained`. No `--force` or `--disable-eviction` flags were used. Stateful workloads `postgresql-4` and `etcd-dns-2`, cert-manager components, service replicas, CSI controllers, and two GitHub Actions runners were evicted. Node 3 remained `Ready,SchedulingDisabled`, with its control-plane static pods and DaemonSet pods still running. A drain does not stop a kubeadm control plane or its local etcd member.

Immediately after draining, the recreated `postgresql-4` and `etcd-dns-2` pods were **Pending**. Scheduler events state `1 node(s) were unschedulable, 2 node(s) didn't match pod anti-affinity rules`. Each requires a distinct third node. CloudNativePG still had primary `postgresql-5` on node 1 and two ready instances, but reported `Waiting for the instances to become active` and `Ready=False` because the third cannot schedule. `etcd-dns-0` and `etcd-dns-1` remained running on nodes 1 and 2. Cert-manager controller had two ready replicas on nodes 1 and 2; cainjector and webhook also rescheduled ready.

Longhorn impact: after drain, four still-attached volumes were `degraded`, with two running replicas on nodes 1 and 2. Four detached volumes were `unknown` (two Renovate volumes plus the DNS and PostgreSQL PVCs from node 3). The node 3 replicas for the four attached volumes became `stopped` and have `failedAt=2026-11-17T19:37:56Z`. This may appear as an error/ERR in the Longhorn UI; do not claim every UI error is benign without identifying the specific volume and replica. Longhorn engine replica maps for attached volumes listed only nodes 1 and 2. Neither application nor storage has full three-way redundancy during this maintenance window. No replica counts, anti-affinity settings, or Longhorn policies have been altered. Preserve the NVMe filesystem, especially `/mnt/nvme/storage-1`, until a safe restore/rebuild strategy is established.

**Current hold:** do not power off node 3, edit partitions, or declare the cluster fully healthy. Verify any reported Longhorn ERR against the named replica/volume, confirm recovery/backup and application availability with two members, and decide whether the pending third members should remain Pending until node 3 returns. Do not bypass anti-affinity merely to make dashboards green.

- Kubernetes API `kubectl --context admin@k8s-pi-cluster-tailscale get --raw=/readyz?verbose` passed all listed checks, including `etcd` and `etcd-readiness`. No unavailable aggregated APIService was reported. All three nodes remained `Ready`, with node 3 still `SchedulingDisabled`; node 3's static control-plane pods and DaemonSets were still running.
- Service endpoints: `postgresql-rw` resolved only to the pod on node 1 (`postgresql-5`); `postgresql-ro` resolved to node 2 (`postgresql-6`); `postgresql-r` resolved to both. Read-only SQL in the pods using `psql -U postgres -d postgres -tAc 'SELECT pg_is_in_recovery()'` returned `f` on pod 5 (primary) and `t` on pod 6 (replica). The cert-manager and Traefik services had ready endpoints on nodes 1/2. Both DNS etcd service endpoints belonged to nodes 1 and 2.
- End-to-end HTTPS via the two node addresses with the analytics ingress hostname and normal certificate verification returned `HTTP 200` through both node 1 and node 2: `curl --resolve analytics.lab.philprime.dev:443:10.1.1.1 https://analytics.lab.philprime.dev/` and the same with `10.1.1.2` (the actual checks suppressed response bodies). This validates that particular ingress/API path, not every application endpoint.
- DNS etcd logs from both live pods repeatedly warned that the peer `etcd-dns-2` hostname could not be resolved. This is consistent with the third pod being Pending because of anti-affinity, **not** evidence that both surviving members are healthy by itself. Read-only `etcdctl endpoint health` with mounted client certificates and the per-pod DNS hostname succeeded on each of `etcd-dns-0` and `etcd-dns-1`, committing a proposal in ~198 ms and ~96 ms respectively. An earlier test aimed at `https://127.0.0.1:2379` failed TLS hostname verification because the server certificate has no loopback IP SAN. That first failed _test_ was corrected by using the pod's DNS hostname; do not report the certificate mismatch as an etcd outage.
- PostgreSQL primary logs document the earlier switchover and successful promotion to timeline 3. A brief WAL archiving error during the transition said archiving was refused while switchover was in progress. Subsequent cluster status previously reported continuous archiving working, but with the third pod Pending the CloudNativePG resource reported `Ready=False`. - Longhorn manager logs show the node 3 replica connections closed during drain (`EOF`), engine entries for node 3 in `ERR` mode removed, and volumes becoming degraded. The four attached volumes continued with running replicas on nodes 1/2. Logs also show replica replenishment deferred and a separate `guaranteed-instance-manager-cpu` setting sync warning while volumes are attached; neither is a reason to edit settings during this stability check. The two previously detached Renovate volumes and the two newly detached PVCs for the Pending DNS/PostgreSQL pods remained `unknown` rather than demonstrably healthy.
- `kubectl get pods -A --field-selector status.phase!=Running,status.phase!=Succeeded` returned only `etcd-dns-2` and `postgresql-4`, both Pending due to hard anti-affinity against the two remaining schedulable nodes. These pending pods and degraded storage mean **stable enough to answer the checks above, not fully healthy or fully redundant**. We have not validated backup restorability or an actual loss of either remaining node.

## Migration storage constraints and operator preference

The operator does not have a separate backup drive and accepts a fresh reinstall if node 3 fails. They want to retain SSH access as long as possible and are open to using the local computer for temporary storage. This does **not** change the need for explicit confirmation before overwriting the NVMe or stopping control-plane services. Read-only inspection found:

- Local workspace filesystem: only ~21 GiB free. A full copy of the ~46 GiB used NVMe filesystem will not fit here.
- NVMe content sizes (`du -xhd1 /mnt/nvme`): `containerd` ~21 GiB, Longhorn `storage-1` ~25 GiB, `kubelet` ~3.4 MiB. NVMe is mounted at `/mnt/nvme` as a single ext4 filesystem with no submounts. Its DOS partition table has one partition starting at sector 2048 and filling almost the whole ~465.8 GiB disk.
- SD root earlier showed ~47 GiB available, enough _in principle_ for the Longhorn replica directory alone, but not all NVMe content together. Copying live Longhorn replica data is not automatically a valid restore procedure. Do not confuse a file copy with a recoverable snapshot, and do not erase the originals on this basis alone.
- Possible approach under evaluation: continue booting from the SD while the NVMe is made inactive, then either resize its ext4 filesystem **offline** and create boot/root partitions in the freed space (preserving the old partition) or prepare a separate temporary copy and rebuild. In-place shrinking/repartitioning is hard to reverse and has no verified whole-device backup. The correct Pi 5 boot-partition selection and OS/root configuration need verification before choosing this approach. Search results pointed to official Raspberry Pi boot documentation at https://www.raspberrypi.com/documentation/computers/config_txt.html and https://www.raspberrypi.com/documentation/computers/raspberry-pi.html, but a direct documentation fetch returned HTTP 403. No bootloader behavior was assumed from that failed fetch.
- At the time of this inspection, no Kubernetes services were stopped, no NVMe filesystem was unmounted or resized, and no data was copied.

## Stop Kubernetes work on node 3 while retaining SSH

The operator explicitly authorized stopping active work on node 3. Before stopping, nodes 1 and 2 were Ready with healthy local API/etcd pods. The virtual IP `10.1.233.1` was on node 1, not node 3. SSH to node 2 briefly showed a changed host key, then the operator resolved it independently; a later SSH connection with `StrictHostKeyChecking=yes` succeeded. We did not edit local `known_hosts`.

On node 3, `systemctl is-active` initially showed `kubelet`, `containerd`, `keepalived`, and `haproxy` active. `crictl pods --state Ready` showed five DaemonSet pods plus the four kubeadm static control-plane pods. A simple `systemctl stop kubelet` **does not stop** already-running pod sandboxes: a second `crictl` listing still showed all nine as Ready. The controlled shutdown used:

```bash
ssh -i ~/.ssh/k8s_cluster_id_ed25519 pi@10.1.1.3 'sudo -n systemctl stop kubelet'
# With kubelet inactive, stop the five known DaemonSet sandboxes via crictl stopp.
# Then stop scheduler, controller-manager and API server sandboxes.
# Stop the etcd sandbox last.
ssh -i ~/.ssh/k8s_cluster_id_ed25519 pi@10.1.1.3 'sudo -n systemctl stop containerd'
```

The actual `crictl --runtime-endpoint unix:///run/containerd/containerd.sock stopp` commands targeted the pre-inspected sandbox IDs individually/grouped by role. All reported `Stopped sandbox ...`. Afterward `crictl pods --state Ready` returned no entries before containerd was stopped. `systemctl is-active kubelet containerd ssh keepalived haproxy` then returned `inactive`, `inactive`, `active`, `active`, `active`, respectively. Keepalived and HAProxy were intentionally left active on the SD-root OS for now; they are not holding the NVMe filesystem open, and SSH remains available. The NVMe remains **mounted read/write** at `/mnt/nvme`, but `fuser -vm /mnt/nvme` listed only the kernel mount itself, no user processes. `findmnt -R /mnt/nvme` listed only `/dev/nvme0n1p1` mounted there. No unmount, filesystem check, filesystem resize, partition edit, reboot, or file copy has been performed. The surviving Kubernetes API returned `ok` from `/readyz` after shutdown, and direct SSH to node 2 succeeded. Kubernetes pod/node status may lag once kubelet stops, so use local process and runtime checks as the shutdown evidence.

At the operator's request, Keepalived was then stopped **before** HAProxy on node 3, to prevent it from acquiring the virtual IP without a functioning load balancer:

```bash
ssh -i ~/.ssh/k8s_cluster_id_ed25519 pi@10.1.1.3 'sudo -n systemctl stop keepalived'
ssh -i ~/.ssh/k8s_cluster_id_ed25519 pi@10.1.1.3 'sudo -n systemctl stop haproxy'
```

Verification on node 3 returned `keepalived=inactive`, `haproxy=inactive`, `ssh=active`. Node 1 still carried `10.1.233.1/32` on `eth0`, and the surviving Kubernetes API still returned `ok` from `/readyz`. `fuser -vm /mnt/nvme` again listed no user processes, just the kernel mount. The NVMe has **not** yet been unmounted or modified. If node 1 fails while node 3's Keepalived is stopped, node 2 is the only remaining standby for the VIP.

## Check for lingering containerd shims

The operator saw many `containerd-shim-runc` entries in `htop` and asked for a process check. A fresh `ps -C containerd-shim-runc-v2 -o pid,ppid,stat,etime,args` over SSH on node 3 showed **one** remaining shim, PID 80074, parent PID 1, with an elapsed lifetime of ~91 days. `ps --ppid 80074` showed no children. Its cgroup was `/system.slice/containerd.service`; its working directory and log descriptors were under `/run/containerd/io.containerd.runtime.v2.task/k8s.io/`, not the NVMe mount. `ps` did not find any running `containerd`, `runc`, `pause`, `kubelet`, `flanneld`, `longhorn`, or `etcd` process beyond that shim; both kubelet and containerd units were inactive. `fuser -vm /mnt/nvme` still showed only the filesystem's kernel mount and no user-space process. This looks like an old orphaned shim rather than active Kubernetes work, but its exact former container was not identified. No process was killed or cleaned up. A follow-up check resolved the apparent multiplicity: `ps -T -p 80074 -o pid,tid,ppid,stat,comm` showed 13 threads of the **same** shim process PID 80074, including TIDs 80075, 80077, and 80078. `ps -p 800074,800075,80077,80078,80074,80075 -o pid,ppid,stat,comm` returned only process 80074. `htop` was displaying the threads as separate rows; it was not showing numerous independent active containerd shims. No need to kill the process to make the mount available, based on the observed `fuser` result. At the operator's request, checked load before deciding whether termination would help: `ps -p 80074 -o pid,ppid,stat,%cpu,%mem,rss,etime,comm` showed state `Sl`, CPU 0.0%, RSS 7,712 KiB, memory 0.0%; `uptime` showed load averages 0.04/0.16/0.27. Stopping this idle orphan would not materially reduce load. It was not stopped at that point.

The operator later pasted `top`/`htop` output with macOS `/System/Library/...` and `/Applications/...` processes, user `Philip`, and 64 GiB RAM. That was from the **local Mac**, not node 3. It showed no local `containerd` process, but its high load and 24.4 GiB process were unrelated to the Raspberry Pi's remaining shim. The operator explicitly asked to stop containerd completely on node 3. We rechecked that PID 80074 was the same orphaned `containerd-shim-runc-v2` (parent PID 1, namespace `k8s.io`) and sent it `sudo kill -TERM 80074`, not SIGKILL. A subsequent `ps -C containerd-shim-runc-v2` showed no shim processes. On node 3, `containerd=inactive`, `kubelet=inactive`, `ssh=active`; `fuser -vm /mnt/nvme` still showed only the kernel mount. Kubernetes API `/readyz` still returned `ok` from surviving control-plane nodes. The NVMe is **still mounted** and no filesystem or partition operation has occurred. No service was disabled or masked, so a reboot could start the services again.

## Recovery tradeoff discussed before disk work

The operator accepts that there is no full backup and that node 3 could be rebuilt from scratch if necessary. This is not just a backup decision: the proposed NVMe layout requires an offline ext4 shrink, partition edits, boot/root filesystem creation, and validation of Pi 5 partition selection and boot order. For four **attached** Longhorn volumes, read-only checks showed two running replicas on nodes 1 and 2 after node 3 was drained; if node 3's disk is lost, Longhorn should be able to rebuild lost replicas from surviving healthy copies once a third storage node returns, but recovery has not been tested. Detached volumes report `unknown`, so their restorability cannot be inferred from that status alone. With node 3 out, both the Kubernetes control plane and DNS etcd have only two of three members, PostgreSQL has a primary and one replica, and attached Longhorn volumes have only two active replicas. Any failure or data loss on node 1 or 2 during this window can turn a recoverable node-3 loss into an outage or data loss. The operator is aware of and weighing that risk. At that stage no NVMe disk modifications had been performed yet.

## Offline NVMe inspection after accepting the risk

The operator accepted the in-place resize/rebuild risk. Node 2 was inspected as a working reference: its NVMe has a 512 MiB FAT `nvme0n1p1` mounted at `/boot/firmware`, then an ext4 `nvme0n1p2` mounted at `/`; its EEPROM reports `BOOT_ORDER=0xf146`. Node 3 has `BOOT_ORDER=0xf461`, which tries the SD boot first. Raspberry Pi documentation search results indicate the Pi 5 firmware searches for a bootable FAT partition containing the right boot files, even if that partition is not partition 1, and selects Linux root using `cmdline.txt` separately. The direct web documentation fetch returned 403, so this partition-selection detail has not yet been tested on this device. Avoid claiming guaranteed boot success before a physical fallback test.

Node 3 has `/usr/sbin/e2fsck`, `resize2fs`, `sfdisk`, and `mkfs.vfat` available. After confirming that only the kernel mount referred to `/mnt/nvme`, we ran `sudo umount /mnt/nvme` over SSH. A subsequent **read-only** `sudo e2fsck -fn /dev/nvme0n1p1` completed five passes and printed the filesystem summary `386017/30531584 files, 14118032/122096388 blocks`. It reported only that two inode extent trees could be narrower and answered `Optimize? no` due to `-n`. No corruption or forced repair was reported. This check did not resize the filesystem or change partitions. At that point the NVMe was unmounted and SSH still ran from the SD card.

## Plan A chosen and temporary Longhorn copy staged on the SD card

The operator preferred Plan A: after staging the essential Longhorn replica directory, rebuild the NVMe with a standard 512 MiB FAT boot partition and an ext4 root filesystem taking the remaining space, matching node 2. The alternative in-place shrink would leave separate small data and large root partitions with less flexible capacity. Repartitioning and overwriting the NVMe have **not** been authorized or performed yet.

We mounted node 3's original NVMe read-only with `sudo mount -o ro /mnt/nvme`. `findmnt` confirmed `/dev/nvme0n1p1 ext4 ro,relatime`. The original `storage-1` directory used ~25 GiB and the SD card had ~47 GiB available. A new root-owned staging directory `/var/tmp/node3-nvme-storage-1` was created on the SD root filesystem with mode 0700. Then:

```bash
sudo rsync -aHAXS --numeric-ids --one-file-system --info=stats2 /mnt/nvme/storage-1/ /var/tmp/node3-nvme-storage-1/
sudo rsync -aHAXS --numeric-ids --one-file-system --checksum --dry-run --itemize-changes --info=stats2 /mnt/nvme/storage-1/ /var/tmp/node3-nvme-storage-1/
```

The first copy completed with rsync exit 0, reporting 39 entries (29 regular files and 10 directories) and 88,046,832,332 bytes of **logical** file size. These Longhorn replica files are sparse; the original directory used ~25 GiB on disk, while the staged directory used ~23 GiB on disk after `-S` sparse copying. SD root then showed ~31 GiB used and ~25 GiB free. The checksum-mode dry run exited 0, printed **no itemized changes**, reported zero files transferred, and matched all file content/metadata that rsync checks under these options. This is a verified _file-level staging copy_, not a proven Longhorn application restore. The original NVMe filesystem remains intact, mounted read-only; containerd's ~21 GiB of data was deliberately not staged because it can be rebuilt/re-downloaded. Do not erase the original until there is explicit confirmation of the exact destructive step.

Pre-erase path check: `/var/lib/kubelet` on the SD root is a real directory, not a symlink; the old NVMe also contains `/mnt/nvme/kubelet` (~3.4 MiB). `/etc/containerd/config.toml` explicitly sets `root = "/mnt/nvme/containerd"`; `/etc/fstab` still mounts old `/dev/nvme0n1p1` at `/mnt/nvme`. The staged `storage-1` directory contains `longhorn-disk.cfg` and `replicas/`, including Longhorn disk identity metadata.
